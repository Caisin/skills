# KX Design Patterns

用于检查 KX 设计文档是否定义了可实现、可验证的工程契约。

## 设计检查

- 用户能调用什么，成功与失败时看到什么？
- 状态、数据、事务与并发边界是什么？
- 下游 crate、feature、数据库和序列化是否兼容？
- 密钥、认证和第三方协议是否受影响？
- 哪些替代方案被拒绝，为什么？
- 哪些测试能够证明设计成立？
- 大型迁移的总览文档与分步骤文档如何互相引用？

## 推荐模板

```text
问题 -> 用户可观察契约 -> 数据/安全边界 -> 兼容性 -> 替代方案 -> 验证
```

## 常见错误

```text
❌ 用文件修改列表代替行为契约
❌ 写“保持兼容”但没有说明兼容对象
❌ 只写 happy path
❌ 分步骤文档没有总览入口，阶段边界互相矛盾
```

## 正确做法

```text
✅ 为错误、默认值和迁移写具体例子
✅ 将开放问题标为阻塞设计/实现/可延后
✅ 主设计记录总目标和稳定决策，步骤文档记录阶段范围与验收
✅ 实现完成后回填偏差和证据
```
