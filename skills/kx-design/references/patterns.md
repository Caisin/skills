# KX 工程设计检查清单

用于检查设计是否已经形成可实现、可分阶段验收、可在中断后恢复的工程契约。

## 文档形态

- 单一功能使用 `docs/dev/design/<feature-name>.md`。
- 大型功能使用 `<feature-name>/index.md` 和有顺序的阶段文档。
- 同一功能不同时保留单文件设计和目录总览。
- 总览只保存全局决策，阶段文档保存本阶段完整规格。

## 用户与兼容性

- 用户能调用什么，成功和失败时能观察到什么？
- 默认值、状态转换、错误码和幂等重放是否具体？
- 下游 crate、feature、数据库、序列化和已发布 API 如何迁移？
- 哪些相邻能力明确延后或不纳入？

## SeaORM 2 与数据

- entity 是否按业务功能分目录，并使用 dense entity 与生成 alias？
- 表、字段、relation、备注、唯一约束和联合索引是否完整？
- 数据源是否由业务 crate 的 `ext_db_trait!` 拥有？
- `install.rs` 是否是唯一迁移入口，并区分 registry sync 与显式迁移？
- 单库 `SeaTrans`、多库 best-effort、幂等、CAS 和 outbox 边界是否明确？
- SQLite 验收与目标数据库部署前验证是否分开描述？

## HTTP、安全与启动

- DTO、`ctl -> svc -> entity/alias`、`ApiRouter + ApiMeta` 是否闭合？
- API code、权限、公开/认证/受保护、明文/加密和第三方回调是否显式？
- 敏感字段、密钥、审计、外部 provider 失败和重试策略是否覆盖？
- install、serve、route catalog、task registry 和 provider 注入顺序是否在受影响时说明？

## 分阶段执行

- 阶段是否代表可独立交付的业务里程碑，而不是技术任务列表？
- 大型设计是否优先控制在 3 到 6 个阶段；更多阶段是否逐项说明必要性？
- 同一用户流程、契约闭包和验证集是否已经合并？
- entity、svc、ctl、前端和测试是否优先作为阶段内清单或泳道？
- `index.md` 是否有阶段链接、文字状态、最近证据和恢复点？
- 是否标明串行依赖链和并行组？同一串行链是否最多一个阶段为 `进行中`？
- 并行阶段是否无未提交契约依赖、无共享写文件且验证资源互不干扰？
- 是否避免仅为了并行而增加阶段；同一业务闭环是否改用阶段内泳道？
- `- [x]` 是否只用于已通过退出条件的阶段？
- 每个阶段是否说明前置条件、独占文件、退出条件和解除阻塞的下一阶段？
- 并行泳道是否不共享写文件，也不依赖其它泳道未提交的契约？
- 阶段验收是否使用最小充分检查，并把重复的完整回归集中到最终阶段？
- 是否有最终前后端联合验证，而不是只列独立 build？

## 常见错误

```text
❌ 用文件修改列表代替用户可观察契约
❌ 把大型迁移写成一个无法恢复进度的长文档
❌ 按 crate、表、API 或 entity/svc/ctl 技术分层机械拆阶段
❌ 为了提高并行数拆出互相等待、共享文件或无法独立验收的阶段
❌ 每个阶段重复相同的 workspace、前端和端到端验证
❌ 阶段文档各自修改同一共享入口，没有集成负责人
❌ 把 Schema Registry sync 当作删列、改类型或数据回填工具
❌ 把 SeaTrans 描述成跨数据源原子事务
❌ 为 SeaORM 业务重新设计 Toasty、TcMgr 或 baseline
❌ 只写单元测试，不设计 SQLite、目标数据库或前后端联合验收
```

## 正确做法

```text
✅ 先固定行为、错误、不变量和兼容方式，再分配模块
✅ 总览维护阶段门禁和恢复点，阶段文档维护可验收范围
✅ 一个阶段完成一个业务闭环，小任务放阶段内清单或实现泳道
✅ 独立业务里程碑可组成并行组，并由单一集成负责人收口共享入口
✅ 阶段运行聚焦验证，最终阶段再运行完整回归和联合验收
✅ 业务 crate 自有 entity、数据源 alias、install 和功能子目录
✅ registry sync 补缺失对象与备注，复杂 DDL 使用显式迁移和备份
✅ 单库事务、多库顺序、外部副作用和补偿分别说明
✅ 每个阶段结束保持 workspace 可构建，并记录真实验证证据
```
