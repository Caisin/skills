# Source Navigation

用于“实践层写法背后到底该看哪个框架目录”的场景。

格式：问题 -> 回看目录 -> 理由

## 快速对照表

### 1. `#[derive(Sea)]` 生成了什么，为什么和预期不一样？

- 回看目录
  - `derives/sea/`
  - `derives/codegen/`
- 理由
  - 这里定义了宏入口、Alias 生成、Query/Modify/EntitySelect 等代码生成规则

### 2. 为什么业务侧 `qry()` / `sel()` / `save()` 表现是这样？

- 回看目录
  - `derives/codegen/`
  - `crates/sea-orm/`
- 理由
  - 前者决定自动生成方法，后者承接运行期 DB/事务扩展能力

### 3. 事务、连接、数据源注册该怎么理解？

- 回看目录
  - `crates/sea-orm/`
  - `core/`
- 理由
  - 这里能看到 `SeaOrms`、`SeaTrans`、`ext_db_trait!` 等基础能力如何组织

### 4. 第三方平台接入应该放到哪，为什么不是通用 crate？

- 回看目录
  - `sdks/`
  - 必要时对比 `crates/`
- 理由
  - `sdks/` 是集成接入与适配层，`crates/` 是内部通用能力层

### 5. 业务项目该依赖框架仓库哪些能力？

- 回看目录
  - `kx/`
  - `Cargo.toml`
  - `AGENTS.md`
- 理由
  - 这里能看出 facade、workspace 能力分布和当前事实来源

## 使用建议

```text
先回答“业务项目里怎么写”
-> 用 project-skeleton / crud-workflow / sea-usage

再回答“为什么框架这样生成 / 这样限制”
-> 回看本文件给出的框架源码目录
```

不要一上来就深入框架源码，也不要在明显需要源码事实时只靠业务模板猜。


## 常见错误

```text
❌ 一上来就钻框架源码，跳过业务侧模板与现象归类
❌ 明明只是“业务里怎么写”，却直接从 derives/ 或 tools/ 开始读
❌ 只靠业务模板猜，不在需要源码事实时回看对应目录
```

## 正确做法

```text
✅ 先回答“业务项目里怎么写”，再决定是否需要源码回溯
✅ 先按问题类型映射目录，再深入具体 crate 或模块
✅ 需要解释生成或事务边界时，再回到框架源码目录验证
```
