# Karpathy Guidelines Patterns

用于当前仓库内的“小步、可验证、最小改动”开发任务。

## 适用场景

- 在已有 crate 里补一个便捷方法
- 修一个局部 bug，并且希望避免顺手扩 scope
- 需要把“先定义成功标准，再实现”固化成工作流

## 推荐模式

### 1. 先写成功标准

```text
成功标准
1. 新增什么入口 / 修复什么行为
2. 最少跑哪些测试或命令来证明它成立
3. 明确哪些旧行为必须保持不变
```

### 2. 先锁定失败用例

```text
- 新增测试先失败
- 失败原因必须是“功能未实现”，而不是拼写错误/导入错误
- 再补最小实现让它转绿
```

### 3. 只复用现有路径

```text
✅ 优先复用已有 helper / trait / renderer / builder
✅ 新增一层很薄的便捷入口
❌ 为了一个小需求再造一套并行实现
```

## 常见错误

```text
❌ 一边做局部功能，一边把周边模块顺手重写
❌ 用户只要一个入口，却引入一堆可配置参数和抽象层
❌ 完成报告里只有“已完成”，没有测试证据
```

## 正确做法

```text
✅ 每一处改动都能追溯到当前需求
✅ 先跑目标测试，再决定是否扩大验证范围
✅ 最终只报告已经实际验证通过的内容
```
