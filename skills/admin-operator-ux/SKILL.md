# 后台操作者体验

站在高频后台操作者的角度设计、实现和验证完整任务流。目标不是“页面有这个功能”，而是让操作者能快速识别对象、从当前上下文直接行动、明确知道结果，并且不被技术字段和重复跳转打断。

## 用户第一性原则

所有页面和业务模块先回答“操作者要完成什么”，再决定组件、表结构和 API：

1. **最短路径**：常见任务尽量在同一页面或同一 Drawer 完成，不为了一个动作在列表、详情、配置页之间来回切换。
2. **简单明了**：每个控件只表达一个确定语义；空值、默认值和危险动作不能承担多重含义。
3. **数据分层**：首屏展示识别对象、当前状态、影响范围和下一步；技术字段、长文本和审计细节进入详情。
4. **关联处直达**：关联业务数据必须在对应字段、数量或状态附近提供直接查看/维护入口，并保留当前上下文。
5. **最小操作**：减少重复填写、重复确认和跨页面跳转；能由后端一次完成的流程，不让前端串联多个写 API。
6. **边界清楚**：生命周期不同、权限不同或信息密度高的内容，用 Tab、标题分隔线或独立区块组织；Tab 按需加载并显示数量/异常状态。
7. **组件复用**：通用的详情、危险确认、状态反馈、引用选择器、Tab 关联列表优先抽成公共组件，避免每个业务复制一套略有差异的弹框。
8. **允许破坏性重构**：当现有页面或表结构持续阻碍上述目标、造成数据错误/越权/任务丢失时，可以重构页面、API 或 Schema；必须先写清迁移/兼容边界、补回归测试，并删除旧入口或旧字段的歧义，不能为兼容错误模型继续叠加补丁。

改造后必须重新按本节规则复审一次，复审结果区分已验证、静态可证明和待人工点验。

## 适用边界

### 适用

- 后台管理端的列表、详情、编辑、配置、审核、资产和关联数据页面
- 需要同时调整前端交互与后端分页、排序、筛选、权限或异步任务契约
- 对已有页面做操作者视角的体验审查和最小修正
- 从明确的用户反馈中提炼可跨页面复用的后台交互规则

### 不适用

- 品牌站、营销落地页、内容展示页或纯视觉资产设计
- 仅修复单个样式像素且不涉及后台工作流的任务
- 业务规则、Schema 或安全边界尚未明确的非平凡设计；先使用 `kx-design`

## 执行流程

### 1. 先定义操作者任务

先从现有代码、页面和用户描述确认：

- 谁在操作，最常完成什么任务；
- 操作频率、单次数量和最容易出错的步骤；
- 当前入口、选中对象、筛选条件和返回后需要保留的上下文；
- 操作是否高风险、耗时、可撤销，是否需要权限和审计。

只补影响方案的假设。能从仓库核实的，不反问用户。

### 2. 检查完整链路

界面出现控件前，确认后端确实支持对应行为：

- 表格排序必须进入 API 白名单并作用于数据库查询；
- 筛选、全文搜索、分页和导出必须使用同一字段语义；
- 字段编辑必须有独立或明确分组的写入契约；
- 关联数据必须同时做后端权限过滤，不能只靠前端隐藏；
- 批量导入、导出、同步等耗时操作必须进入持久化异步任务。

没有打通后端契约时，不保留虚假的排序图标、按钮或成功提示。

同时逐项证明前端交互闭环：

- 按钮、可点击字段和菜单项必须绑定真实 handler，不能只渲染外观；
- Modal、Drawer 和 Tab 必须完成注册、数据传入和 `open` 调用，关闭后返回原上下文；
- 提交必须调用对应写 API，成功后刷新受影响数据，失败时保留输入并显示可行动错误；
- 详情、编辑、删除、审核、批量、导入导出等业务动作要与页面的任务目标逐项对照，不能因为列表能加载就判定功能完整。

静态代码只能证明绑定和调用链存在。弹层是否真正打开、路由是否可达、权限态下是否可操作、保存后是否正确刷新，必须通过组件测试或浏览器点验证明。

### 3. 组织操作界面

按以下顺序决定布局：

1. 表格优先展示识别对象、判断状态和决定下一步所需字段。
2. 对应数据的常用维护入口放在对应字段上，点击后打开聚焦编辑。
3. 低频、技术性、长文本字段进入详情，不占据列表主视野。
4. 多字段表单按业务关联性分块，每块有清晰标题，保持一到两列稳定网格。
5. 同一主对象下、生命周期相对独立的关联数据用 Tab 管理，并显示数量或状态。
6. 批量操作依赖选择状态出现，常用全局操作放紧凑工具栏，危险操作二次确认。

### 4. 保持上下文和反馈

- 打开编辑、详情和关联记录后，关闭时回到原筛选、页码、排序和滚动位置。
- 路由参数可直接打开详情或指定 Tab，便于通知和外部链接直达任务。
- 保存只刷新受影响数据，成功后明确反馈；失败时保留输入并展示可行动错误。
- 加载、空数据、无权限、部分失败和异步处理中必须有不同状态。
- 图标按钮使用现有图标库并提供 tooltip；可点击字段要有一致的视觉提示和键盘焦点。

### 5. 验证真实工作流

至少验证一条完整主路径，而不只验证组件能渲染：

```text
进入列表 -> 定位对象 -> 从字段发起操作 -> 修改并保存 -> 列表刷新 -> 再次打开确认
```

同时检查：入口 handler、Modal/Drawer 打开、写 API、保存刷新、真实后端排序/筛选、权限边界、路由深链、空态、失败态、窄屏文本和布局。前端改动运行目标产品 typecheck；可运行浏览器时用 Playwright 点验关键路径。

## 核心规则

1. **对象优先**：列表首先帮助操作者认出对象，而不是展示数据库结构。
2. **字段即入口**：对字段的常用操作，从该字段直接进入；不要为每项都堆操作列按钮。
3. **动作要聚焦**：点击字段只编辑该字段或同一业务分组，不打开无关的超长表单。
4. **详情承载低频信息**：技术键、执行编码、完整备注和审计信息进入详情。
5. **关联数据不混写**：主体、设备、认证人等独立生命周期数据使用独立 API，在父对象上下文内通过 Tab 或聚焦弹窗维护。
6. **信息按任务分组**：多字段表单按账户、主体、认证、设备、状态等业务块组织，不按数据库列顺序平铺。
7. **空间服务于高频操作**：表格操作区只留高频命令；图标尺寸、按钮高度和内间距与同一工具栏保持一致。
8. **前后端行为一致**：可见排序、筛选、授权、导入和导出都必须有真实后端实现。
9. **耗时任务异步化**：批量操作立即返回任务，持续展示进度、成功数、失败数和失败原因。
10. **管理员不是默认用户**：普通用户只看到获授权数据，管理员全量访问也必须由后端明确判定。
11. **交互必须闭环**：控件存在、列表能渲染或 API 文件存在都不等于功能完整；必须验证入口、弹层/路由、写入、刷新和失败反馈的连贯行为。从 Drawer 或 Modal 打开的子弹层必须显示在父弹层之上，并保持遮罩、焦点和关闭顺序一致。
12. **引用选择可维护**：凭证、主体、字典等独立主数据的下拉框应占满字段剩余宽度，在面板底部提供快捷新增入口，并把刷新作为紧贴选择器右侧的 suffix；快捷新增在当前页面弹窗完成，完整维护页面的跳转放在该弹窗内。新增完成后自动回填并刷新选项，不能要求操作者关闭整个表单重来。
13. **共享秘密不复制**：业务对象已单独保存账号标识、多个对象可共用同一秘密时，凭证选择器应允许只含秘密的凭证类型；不要为每个对象重复创建带账号的凭证。
14. **公共历史不按业务复制**：多个业务共用同一导入导出运行模型时，只提供一个公共历史页面，按业务定义筛选并统一下载原文件、结果和错误明细；不要为每个业务复制记录表、API 或历史页面。
15. **后端为流程提供能力**：一个用户动作需要多个 API 才能完成时，优先增加面向任务的后端聚合/事务 API；前端只编排独立查询，不在浏览器串联多个有副作用的写请求。
16. **Tab 是信息分层工具**：只有共享主对象上下文且可独立加载/授权的数据才进 Tab；Tab 必须保留父对象、按需加载、展示数量或异常，并支持从关联数据直接回到业务对象。
17. **组件化公共弹框**：重复出现的确认、详情、选择、错误和异步任务反馈应收敛到公共组件；公共组件必须保留业务动作、权限和错误上下文，不以“通用”名义隐藏关键影响范围。
18. **引用配置可维护**：Provider、通道、字典和推送端点等下拉选项必须说明数据来源；有后台写入口时在选择器旁提供“新增”和刷新，新增打开当前页快捷弹窗，完整维护跳转位于弹窗内；无后台写入口时明确标注由 App/小程序或业务系统维护，只提供刷新，禁止伪造“新增”按钮。
19. **低频说明默认收起**：配置步骤、外部文档和排障说明较长时，默认只显示简短标题与展开入口；步骤和相关链接一起展开，不能长期占据列表或表单首屏。
20. **业务表单不暴露原始 JSON**：面向业务操作者的 payload、扩展参数和协议对象必须拆成有业务名称、组件类型、默认值和校验的明确字段；无法稳定定义语义的未知键不进入普通表单。只有明确面向技术运维、确实需要任意结构且没有可靠 schema 时，才允许在标注风险的专家模式中使用 JSON 编辑器。
21. **多关联项用表格维护**：关联号码、用户、角色等可能增长到较多记录时，主维护面使用可分页表格展示并提供逐项操作；选择器只用于独立的添加步骤，不能用一个超长多选框同时承担展示、删除和保存。

## 自我演进协议

后续用户对后台操作方式给出明确修正时，在完成页面改动的同一任务中检查本 skill：

1. 在 `references/evolution.md` 记录匿名化反馈、适用上下文和被修正的规则。
2. 判断它是一次性产品要求，还是可跨两个以上后台场景复用的稳定模式。
3. 稳定模式同步写入 `SKILL.md` 或 `references/patterns.md`，并新增或修改至少一个 eval。
4. 新规则与旧规则冲突时，明确标记替代关系，不把两条冲突规则并列保留。
5. 不把截图像素、业务名称、个人路径或敏感数据提升为通用规则。
6. 运行 skill 全量校验，并在提交中准确记录验证结果。

用户明确说“以后都这样”“形成规范”或重复指出同类操作问题时，默认视为稳定模式；仅针对单页面的特殊例外留在业务代码或设计文档中。

## 常见错误 vs 正确做法

### 常见错误

```text
❌ 每行固定放查看、编辑、删除、更多等一长串按钮
❌ 点击某个字段却打开包含全部数据的巨型表单
❌ 把主体、认证人、设备字段复制进账户表并一起保存
❌ 前端显示排序图标，后端仍按固定顺序返回
❌ 批量任务在 HTTP 请求中同步执行，超时后操作者不知道结果
❌ 只验证 typecheck，没有走一遍真实操作路径
❌ 按钮、弹窗和 API 各自存在，但没有核对 handler -> open -> submit -> refresh 是否连通
❌ 每接入一个导入业务就新增一套历史表、历史 API 和历史页面
```

### 正确做法

```text
✅ 点击主体列直接维护主体，点击设备数直接进入设备 Tab
✅ 技术字段留在详情，列表组合展示相关时间或状态
✅ 复杂编辑按业务块分组，关联数据使用独立 API 和 Tab
✅ 批量任务展示进度与逐条失败原因，刷新页面后仍可追踪
✅ 通知深链直接打开对应记录详情，并保留返回上下文
✅ 逐项点验按钮、弹层、写入、局部刷新和失败保留输入，并记录缺失的业务动作
✅ 引用型下拉在当前字段旁提供快捷新增与刷新，新增弹窗内再提供完整维护入口
✅ 所有业务的导入导出记录进入同一公共历史页，按定义、方向和状态筛选
```


```text
- 保留识别账户、主体、认证人、状态和关键时间所需列，技术键进入详情。

- 验证字段点击、保存刷新、权限、深链和窄屏布局。
- 若这是新的稳定反馈，同步更新 evolution、patterns 和 eval。
```
