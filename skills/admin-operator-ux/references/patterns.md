# 后台操作者界面模式

本文提供 `admin-operator-ux` 的可复用决策模式。先复用仓库现有 Vben、VXE Grid、Drawer、Modal、Tabs 和公共业务组件，不新增平行组件体系。

## 1. 列表信息优先级

### 用户任务检查

开始改代码前，先写出操作者的最短路径：

```text
识别对象 -> 判断状态/影响 -> 在当前上下文行动 -> 得到结果 -> 原条件下确认
```

若路径中同一动作需要跨两个以上页面，先检查能否用详情 Drawer、关联 Tab 或后端一次性 API 收口；只有权限边界或独立生命周期确实要求时才保留跳转。

每个列表字段先归类：

| 层级 | 目的 | 放置方式 |
| --- | --- | --- |
| 一级 | 识别对象、判断状态、决定下一步 | 固定或首屏可见列 |
| 二级 | 高频比较、常用维护 | 普通列，可点击编辑 |
| 三级 | 技术键、长文本、审计和低频信息 | 详情 Drawer |
| 四级 | 独立生命周期的关联记录 | 详情/编辑中的 Tab |

列表不要逐列映射数据库字段。多个时间可以组合为“创建 / 更新”或“开始 / 完成”，多个数量可以按任务语义组合，但不要把含义不同的数据压成难以扫描的字符串。

### 操作区

- 全局高频动作放表格工具栏，使用与相邻控件一致的紧凑尺寸。
- 选中记录后才有意义的批量动作放选择态工具栏，并显示已选数量。
- 单行高频编辑优先由字段承载；无对应字段的命令才进入操作列。
- 危险、低频命令进入更多菜单，并显示对象名称的二次确认。
- 不为“详情”固定占一个按钮；主要标识字段通常就是详情入口。

## 2. 字段直达编辑

适合字段直达编辑的条件：

- 操作者能从列名和当前值预期点击结果；
- 写入目标明确，能限制在单字段或同一业务分组；
- 修改权限可独立判断；
- 保存后能局部刷新并立即看到结果。

推荐映射：

```text
账户名 -> 账户详情或账户基本信息
主体名称 -> 主体维护
认证人 -> 认证人维护
设备数量 -> 设备 Tab
APP 数量 -> APP Tab
状态 -> 状态维护或状态流转
```

可点击字段使用统一 class，提供 hover、focus-visible 和 tooltip/标题，不依赖颜色作为唯一提示。纯文本选择、复制或跳转是主要行为时，不要强行改成编辑入口。

## 3. 表单分块

### 使用分块的时机

- 字段超过约 8 个；
- 同一表单同时包含身份、配置、时间、状态、备注等不同语义；
- 不同字段组由不同权限或 API 维护；
- 操作者只会频繁修改其中一部分。

### 布局规则

- 使用有标题的无框 section、Divider 或 Tabs；不要把卡片嵌套在卡片内。
- 桌面端通常使用稳定两列网格，长文本、地址、备注和上传区域跨两列。
- 时间使用 DatePicker/RangePicker，枚举使用 Select，布尔值使用 Switch/Checkbox。
- 只读字段使用详情展示或禁用态组件，但不要让只读值看起来可以提交。
- 保存按钮明确作用范围；独立 API 管理的分块独立保存。

## 4. 关联数据 Tab

当多个数据集合共享同一个主对象上下文、但拥有独立查询/保存/权限/生命周期时使用 Tab，例如：

```text
账户信息 | 主体信息 | 认证人 | 设备 | APP 列表 | 审计记录
```

约束：

- Tab 标题可显示记录数量或异常状态。
- 首屏只加载当前 Tab；切换后按需加载，避免详情打开被所有关联接口阻塞。
- 路由或 Drawer 状态支持指定初始 Tab，使列表字段和通知能直达。
- 每个 Tab 使用归属实体的 API，不通过主表写入关联实体快照。
- 关闭后保留父列表筛选、页码和滚动位置。

只有少量、同生命周期且必须一起提交的字段才放同一表单，不要为了视觉整齐滥用 Tab。

## 5. 筛选、搜索和排序

- 高频且区分度高的筛选常驻；其余放“更多筛选”。
- 多个文本字段可由同一全文搜索覆盖时，不再为每个字段放输入框。
- 业务键、执行编码等长枚举使用可搜索下拉框，并按当前权限返回候选项。
- 排序事件传递明确的字段和方向；后端以白名单映射数据库列。
- 翻页、刷新、详情返回和浏览器前进后退应保留查询状态。

### 可维护的引用选择器

凭证、主体、认证人、字典项等由独立页面或 API 管理的引用数据，不应退化为手填编码：

- 下拉框展示操作者可识别的名称，值只保存稳定 ID 或 code；
- 下拉面板底部提供快捷新增，字段旁只保留刷新；快捷新增在当前页面打开聚焦弹窗；
- 选择器占满字段剩余宽度，刷新按钮作为紧贴右侧的 suffix，不让低频图标挤窄主要输入区域；
- 完整维护页面的跳转放在快捷新增弹窗内，不与新增按钮并列占用字段操作区；
- 新增成功后自动回填新值并刷新选项，复杂维护可从弹窗在新标签页打开主数据页面；
- 新增、维护和刷新使用图标按钮与 tooltip，保持选择器宽度稳定；
- 服务端仍校验引用对象存在、状态可用且类型匹配，不能只依赖前端过滤。
- 业务表已经保存账号、多个对象可能共享同一密码或密钥时，选择器应允许只保存秘密的凭证类型；只有登录标识也由凭证拥有时才要求账号密码组合，避免按业务对象复制相同秘密。
- Provider 配置选择器在字段旁提供“新增”和刷新；新增在当前页弹窗完成，弹窗内提供“前往完整维护页面”。App/小程序上报的推送端点属于只读引用，应显示来源说明和刷新入口，不提供无法完成的后台新增。

### 配置指引

- 多步骤配置说明默认折叠，只显示标题和明确的展开入口；
- 展开后同时显示步骤与相关文档链接，收起时一并隐藏；
- 折叠状态必须可被键盘操作，并通过 `aria-expanded` 暴露给辅助技术；
- 简短且直接影响当前输入的校验提示仍就近常显，不要塞进折叠区。

## 6. 批量和耗时操作

- 导入入口使用统一导入组件，提供模板下载、文件选择、格式校验和任务状态。
- 支持粘贴时，明确一行一个值，并在提交前去空、去重和显示有效数量。
- HTTP 请求只负责创建持久化任务；前端展示排队、执行中、成功、部分失败、失败。
- 结果至少包含总数、成功数、失败数和可定位的逐条原因。
- 导出沿用当前筛选和排序语义，产物完成后提供明确下载入口。
- 数据量为零时不创建空执行日志；只更新必要调度状态。

### 公共导入导出历史

多个业务已经共享同一运行模型、任务状态和文件引用时，历史查看也必须复用一个公共页面：

- 统一展示当前操作者有权查看的全部业务定义运行，按定义、方向和状态筛选；
- 在同一记录上提供原文件、结果文件和错误明细入口，并明确文件过期状态；
- 业务页面只负责发起任务和跳转公共历史，不复制运行记录表、列表 API、下载 API 或历史弹窗；
- 只有业务存在独立且不可被公共运行表达的逐项恢复状态时，才保留业务明细表；它仍不等于需要复制一套历史页面。

## 7. 详情、弹窗和路由

- 快速查看使用 Drawer，避免离开列表上下文。
- 聚焦编辑使用 Modal；字段多或需要关联导航时使用与详情一致的分组/Tab 布局。
- 独立、可分享或长时间工作的流程使用路由页面。
- 通知链接包含记录 ID，页面加载后自动打开详情，而不是只跳到列表。
- 一个页面的加载失败不得清空已有 Tab；异步错误应被页面边界捕获并展示可重试状态。

### 破坏性重构判断

当旧字段、旧表或旧 API 让用户无法区分所有者、状态、影响范围或操作结果时，允许直接重构：

1. 记录旧模型造成的具体错误路径和受影响数据；
2. 设计迁移、兼容窗口和回滚边界；
3. 先补覆盖旧行为与新行为的回归测试，再删除歧义入口；
4. 前端不保留“看起来还能用”但语义不一致的兼容控件。

重构不是默认选项。若详情、Tab、公共组件或一个面向任务的 API 已能解决问题，应优先选择可逆的小改动。

## 8. 后端能力与公共组件

- 前端一次提交涉及多张表、状态转换或审计时，后端提供一个事务边界明确的动作 API，返回完成该页面所需的聚合结果。
- 仅把多个 GET 并行请求用于互不依赖的筛选项；共同组成一个详情对象的数据由后端聚合返回，禁止按 ID 循环请求分页接口。
- 公共弹框至少统一关闭清理、加载/失败态、危险确认和成功刷新行为；业务差异通过显式 props/slots 表达。
- 关联数据的数量、异常和最近时间优先放在 Tab 标题或父字段附近，避免操作者必须打开多个页面才能判断影响。

## 9. 权限和安全

- 列表、候选下拉、详情、导出和关联数据使用同一后端授权范围。
- 普通用户的数据过滤必须在查询层执行；前端隐藏按钮只是体验优化。
- 无权限时不提供误导性入口；必要时展示只读值及无权限原因。
- 管理员全量访问使用明确角色/能力判定，不通过缺少过滤条件隐式实现。
- 危险操作展示影响对象和范围；批量危险操作必须再次确认数量。

## 10. 验收清单

### 交互闭环审计

对每个主要业务动作建立一条可追踪链：

```text
可见入口 -> click/command handler -> Modal/Drawer/路由 -> 初始数据
-> 校验 -> 写 API -> 成功/失败反馈 -> 列表或详情刷新
```

- 静态审计记录每一环的文件和符号；任何一环缺失都标记为功能缺口，不用“页面已存在”掩盖。
- 对动态注册、条件权限、弹层可见性和刷新结果，用组件测试或 Playwright 点验；只读代码不能将这些项标为已通过。
- 按页面任务清单核对动作完整性。存在查询接口不代表编辑、删除、审核、导入导出、撤销或重试已实现。
- 输出区分“静态已证明”、“测试已证明”和“待浏览器/真实后端验证”，不混合推断与证据。

```text
[ ] 主要对象能在首屏快速识别
[ ] 主要按钮和可点击字段均有真实 handler
[ ] Modal/Drawer 已注册、可打开并获得正确上下文
[ ] 写操作调用正确 API，成功刷新且失败保留输入
[ ] 操作列没有可由字段承载的重复按钮
[ ] 点击字段打开预期的聚焦编辑或关联 Tab
[ ] 多字段表单按业务关联分块，长字段不会挤压布局
[ ] 排序、筛选、分页、导出与后端语义一致
[ ] 普通用户和管理员的数据范围分别验证
[ ] 批量任务可恢复查看进度和失败明细
[ ] 共用运行模型的导入导出历史已收敛到一个公共页面
[ ] 保存失败保留输入，成功后只刷新必要数据
[ ] 通知/深链能直接打开目标详情
[ ] 加载、空数据、无权限、部分失败状态可区分
[ ] 图标、按钮高度、内间距与同一工具栏一致
[ ] 窄屏和长文本下无溢出、遮挡或布局跳动
[ ] 常见任务不需要无意义的跨页往返，关联数据可在当前上下文直达
[ ] 多写操作已收口为后端事务/聚合 API，前端没有串联副作用请求
[ ] 重复弹框已复用公共组件，业务权限和影响范围仍然可见
[ ] 按新规则完成第二轮复审，并记录静态证据与人工点验缺口
```

## 常见错误

```text
❌ 把 CRUD 四个按钮复制到每一行
❌ 为了减少列数，把无关字段拼成难读的一列
❌ 关联数据只在前端分 Tab，后端仍允许越权读取
❌ Drawer 内再套多个装饰卡片，降低信息密度
❌ 使用 disabled 排序图标或没有绑定 API 的占位按钮
❌ 每次保存后重置全部筛选并跳回第一页
❌ 用同步 HTTP 承载不确定时长的批量任务
```

## 正确做法

```text
✅ 先判断操作者的高频任务，再决定列表字段和操作入口
✅ 点击对应字段维护对应业务分组，保存后局部刷新
✅ 独立关联数据通过归属 API 和 Tab 管理
✅ 用完整任务路径验证界面与后端行为
```
